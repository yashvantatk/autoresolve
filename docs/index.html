AI proposes the fix. A failing test proves it.

AutoResolve is a Rust command-line tool that reviews Python code with AI agents, fixes the bugs it finds, and keeps only the fixes it can prove. A fix counts as proven when a generated test fails on the original code and passes after the patch, inside a locked-down Docker sandbox.

The problem it solves

AI coding tools are good at proposing fixes and bad at knowing when they are wrong. The developer is left to decide whether to believe a confident patch. Failures seen while building this project:

  • A model approved both shell=True and a string passed with shell=False as "fixes" for shell injection. The second one breaks every normal call, and static checks passed both.
  • A model fixed a bare except: by catching two error types, while the docstring said other errors must propagate. The generated test only covered part of the contract, so the fix was marked proven and was still wrong.
  • Models write tests that can never fail, or can never pass, and then report success.

AutoResolve's rule: no AI claim is trusted until something other than that AI checks it.

How it helps a developer

Fix a bug you describe

fix file.py --issue "bug report" turns your description into a regression test plus a candidate patch. If the text names a function, its docstring becomes the contract the fix must respect.

Review code with a second opinion

review runs reviewer agents, then skeptic agents try to disprove every report. Only findings that survive the challenge continue.

Gate AI-written changes in CI

scan uses free AST rules with no model calls and no API key. It writes SARIF for GitHub code scanning and markdown for pull-request comments.

Give assistants read-only repo knowledge

An MCP server exposes symbols, callers, callees and findings. fix and apply-plan are deliberately not exposed, and a test checks that.

See exactly what happened

Every model turn, tool call, check and decision is written to .autoresolve/events.jsonl. A terminal UI replays any run and shows patches as red/green diffs.

Stay in control

Dry run by default. Unproven fixes are never applied. A policy file limits files and lines per patch and protects paths you name.

Use it to review, fix, gate

  • Review a module or pull request and get findings that were already challenged.
  • Turn a bug report into a reproducing test and a candidate patch.
  • Run the free scan on every pull request.

Don't use it to replace people

  • Replace human review. Read the diff.
  • Check other languages. Only Python is parsed today.
  • Trust results on large repos without testing first.

How it works


It is a multi-agent pipeline run by a deterministic controller. Rust code decides which agent runs next. It is deliberately not an autonomous swarm, because language models skip steps, loop, and approve their own mistakes. Each row below shows what the AI does and what checks it that is not AI.




StepAI doesNot-AI check


ReviewAI Reviewer reads code and reports suspected bugs (one generalist, or three specialists: correctness, security, robustness)Code AST rule hints in the prompt, merge and voting rules


ChallengeAI A skeptic per issue tries to disprove itCode Only confirmed issues continue


ReproduceAI Tester writes a regression testCode Must fail before, for the claimed reason. May not inspect the implementation


GuardAI Guard writer writes a test of ordinary useCode Must pass now and still pass after the patch


FixAI Fixer proposes exact search-and-replace editsCode Edits must match exactly once and obey the policy file


CheckNoneCode Syntax, ruff, bandit, mypy not worse, regression test, behavior guard, your own test command


GateAI Answers four yes/no questions, including whether the patch contradicts the documented contractCode Rust computes accept or reject from the answers


VerdictNoneCode Proven only if the regression test went from failing to passing




Proven fixes go into .autoresolve/plan.json. Fixes without proof are saved as unproven suggestions and are never applied by default. apply-plan re-checks the policy, rehearses on a scratch copy, writes the files, then runs the saved tests. The apply is all-or-nothing.



Where the model runs and what it can touch


    
  
  • Sandbox: generated tests run in Docker with no network, a read-only root filesystem, all capabilities dropped, 512 MB of memory and 1 CPU.
    • 
  
  • Grounding: a tree-sitter and SQLite call graph gives agents tools to list symbols, callers and callees, and to read lines.
    • 
  
  • Providers: Gemini or a local Ollama model. Two tiers: a main model for reviewer, skeptic and gate, and a cheaper worker model for tester, guard and fixer, because test failures catch their mistakes while the reviewers' mistakes would be silent.
    • 
  
  • Agent guards: repeated tool calls are refused, a model that never uses tools is stopped, and prose answers are forced into structured output.
    • 




A typical session


autoresolve-cli scan src/                                  # free: AST rules, no model calls
autoresolve-cli review src/billing.py                      # reviewers, then skeptics
autoresolve-cli fix src/billing.py --issue "describe the bug"   # dry run: builds plan.json
autoresolve-cli tui                                        # watch or replay the run, read the diffs
autoresolve-cli apply-plan                                 # re-check policy, rehearse, write, run tests

Interfaces


    
  
  • Terminal UI: live or replay view of the event log with patches as red/green diffs, tests, findings and the gate's answers in colour. It never calls a model or touches the repository.
    • 
  
  • MCP server: read-only tools (scan, symbols, callers, callees, events summary, review). Protocol smoke-tested, not yet tried with a real MCP client.
    • 
  
  • SARIF and markdown: scan and review output SARIF 2.1.0 for code scanning, and review can output markdown for pull-request comments.
    • 
  
  • GitHub Action: the files are written, but the action has never been run on a pushed repository, so treat it as untested.
    •

Limitations and what's next


    
  
  • Proven is not correct. It means the claimed case is fixed. The contract-aware change that targets this gap is implemented but not yet measured.
    • 
  
  • The tester can write tests no fix could satisfy. Nothing is applied in that case, and this is the safe outcome.
    • 
  
  • The call graph matches calls by name only, and only Python is supported.
    • 
  
  • Small local models such as qwen3:4b are unreliable and are treated as a benchmark arm, not a working setup.
    • 
  
  • Nothing has been run against a large real repository yet.
    • 
  
  • Planned: read the pending two-model benchmark runs, test with a real MCP client, run the GitHub Action, a better call graph, more languages, and pre-commit, log-diagnosis and test-generation tools on the same proof layer.
